# repo-artifacts

Derived code-analysis artifacts for The Cyber Toolchain. Generated by
`ctk-code`, a private sibling repository; see `CLAUDE.md` for the rules that
govern this repo.

Nothing here is hand-edited. Every file is regenerable from a local mirror of
the tools' public source repositories plus the analyzer version recorded
inside it. If a file is wrong, fix the analyzer and re-run — do not patch the
artifact, and do not open a pull request against it.

    sbom/<tool>/<head_sha>.json         syft's SBOM inference at that commit + summary + ci_actions
    deps/<tool>/<head_sha>.json         direct dependencies, per manifest path
    authorship/<tool>/<head_sha>.json   attributed commits + adoption markers
    cli/<tool>/<head_sha>.json          mined CLI surface (flags/commands) across tags
    languages/<tool>/<head_sha>.json    language breakdown by bytes at that commit
    aggregate/<run_id>.json             corpus-wide rollup: adoption, licence counts, denominators
    runs/<run_id>.json                  per-run summary: counts, failures, timings

## What these artifacts are

Derived code-analysis facts about 522 open-source security tools: SBOMs,
direct dependencies, AI-authorship attribution, CLI surface history, and
language breakdowns.

## How to read it honestly

**Absence is not emptiness.** `[]` means a tool was analysed and nothing was
found. A **missing key** means the tool was never analysed for that slice. A
tool with no directory here has not been analysed at all — it does not have
zero dependencies, and it is not 0% AI-authored. Don't read silence as a
negative result.

## Known limits

- **SBOMs come from [syft](https://github.com/anchore/syft) 1.49.0**, which
  infers packages from manifests and lockfiles it can find at one commit. It
  does not see vendored code, dynamically resolved dependencies, or anything
  without a manifest. 215 of 522 tools report `components: 0` — usually
  because they are C, shell, or rule-set projects with no package manifest at
  all. That is a real finding about those tools, not a coverage gap in this
  data.
- **CI action usages live in `ci_actions`, a key alongside `cyclonedx` in each
  SBOM artifact — not inside `cyclonedx.components`.** A workflow's use of
  `actions/checkout@v4` is a genuine supply-chain fact (there are roughly
  9,750 such usages across the corpus), but it is not the project's own
  dependency, and earlier analyzer runs counted it as one. That miscount is
  also why the zero-`components` count above rose from 102 tools to 215 once
  it was fixed: those tools had only CI actions, never package dependencies.
- **Dependency licence metadata is sparse.** 87.6% of components carry no
  licence field at all, because syft only reports what a manifest declares.
  The blank is reported as absent, not guessed or inferred.
- **AI authorship undercounts by construction.** Tier 1 counts only
  deterministic markers — `Co-Authored-By:` trailers, known bot identities,
  generator signatures. Squash-merges and rebases strip those, and plenty of
  AI-assisted code carries no marker at all. Tier 2 (config files such as
  `CLAUDE.md` present in a repo) is a fact that supports a weak inference and
  is never rendered as a percentage. The two tiers never merge into one
  number, and neither is a ceiling on actual AI involvement.
