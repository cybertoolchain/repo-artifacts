# CLAUDE.md — repo-artifacts

> Written 2026-07-24, at the same time as the sibling `ctk-code` repo that
> produces everything here.

## What this repo is

The durable output of **code analysis** over the Cyber Toolchain's mirrored
open-source tools: SBOMs, dependency facts, AI-authorship attribution, CLI
surface history, and harvested command output.

**This repo holds data, not code.** The producer is `ctk-code`, a private
sibling repository. Read that repo's `CLAUDE.md` before changing anything
about how artifacts are stored here — the rules it states about provenance and
absence-vs-emptiness bind this repo, because this is where they are actually
enforced or violated.

Nothing here is hand-edited. Every file is regenerable from a local mirror of
the tools' public source repositories plus the analyzer version recorded
inside it. If a file here is wrong, fix the analyzer and re-run; do not patch
the artifact.

## Why the artifacts and the site output are both kept

An artifact here is the *full* derivation — the complete CycloneDX SBOM, every
attributed commit, every mined flag. What the website renders is a trimmed view
of it, generated by an export step in `ctk-code`.

Keeping both is deliberate, and it is the same discipline as `cybertoolchain-data`:
the source and its derivation together are a training pair, and a view that
drops 95% of the data is not a substitute for the data. Never delete an artifact
because the site stopped rendering that field.

## Provenance envelope

Every artifact carries, at minimum:

    tool          canonical name from generator/tct/config/sources.yaml
    repo          owner/name
    head_sha      the exact commit analysed
    analyzer      name and version of the analyzer that produced it
    generated_at  run timestamp

An artifact without an envelope is not trustworthy and should be regenerated
rather than read. `head_sha` is the join key that lets any published claim be
re-derived — it is the reason a reader can check us.

## Absence is not emptiness

`[]` means analysed, found nothing. A **missing key** means never analysed. A
tool with no directory here has not been analysed at all — it does not have zero
dependencies and it is not 0% AI-authored.

This distinction is load-bearing. Collapsing it publishes fabricated negative
claims about real projects.

## Layout

Directories appear as slices land; a slice that has not run yet has no directory
here, and that absence is meaningful.

    sbom/<tool>/<head_sha>.cdx.json     full CycloneDX SBOM (syft)
    deps/<tool>/<head_sha>.json         direct dependencies, per manifest path
    authorship/<tool>/<head_sha>.json   attributed commits + adoption markers
    runs/<run_id>.json                  per-run summary: counts, failures, timings

## Append-only in spirit

History is the point. A tool's artifacts accumulate across `head_sha` values, so
the dependency set and AI-attribution rate can be tracked over time — that
timeline is a genuine finding, not a byproduct. Don't prune old shas to save
space without a deliberate retention decision.

## Growth

Artifacts are small JSON relative to the 67 GB mirror they describe, but there
are ~522 tools accumulating a new sha whenever upstream moves. If this repo ever
outgrows git, the answer is a retention policy or S3 (as `ctk-corpus` did) — not
silently dropping fields.

## Secrets

There should never be any. Input is public source code; output is derived facts.
If a secret ever appears in an artifact, it was scraped out of a public repo —
which makes it an upstream disclosure, not ours to publish. Drop it and note the
finding.
